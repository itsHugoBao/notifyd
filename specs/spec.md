# Spec：可靠的对外通知投递服务

> 状态：**已定稿**（人工评审 + Grok 4.5 交叉评审后确认，评审修订见 git 历史）
> 本 spec 遵循 SDD（Spec-Driven Development）流程，先于任何代码编写，
> 是实现与测试的评审契约（contract）。实现已按本契约完成并通过全部测试。

## 1. 问题陈述

企业内部多个业务系统在关键业务事件发生时（用户经广告引流注册、订阅付款成功、
商品购买导致库存变更……），需要通过 HTTP(S) 调用外部供应商的 API 进行通知。
各供应商 API 互不相同：请求地址不同、Header / Body 格式不同。

业务系统本身：

- **不关心**外部 API 的返回值；
- **只关心**通知请求能被稳定、可靠地送达。

因此我们构建一个内部服务 —— **可靠的对外 HTTP 投递通道**。
业务系统把一个完整成型的 HTTP 请求提交一次，之后由本服务全权负责送达：
容忍供应商的瞬时故障、本服务的进程重启、以及短时间的外部中断。

## 2. 系统边界

### 2.1 在本系统中解决的问题

| # | 能力 | 理由 |
|---|-----|------|
| S1 | 通过内部 HTTP API 接收通知请求，**先持久化、后确认（ack）** | 一旦返回成功，投递责任就归我们。先落盘再 ack 是一切可靠性承诺的地基。 |
| S2 | 异步投递到目标地址，带**超时、重试、指数退避 + 抖动（jitter）** | 供应商故障多为瞬时；退避避免对一个已经不稳的供应商雪上加霜。 |
| S3 | **至少一次（at-least-once）**投递语义（见 §5） | 在纯 HTTP、无接收方配合的前提下，这是唯一诚实可达的语义。 |
| S4 | 终态失败处理：重试预算耗尽后进入**死信（dead-letter）状态**，可查询、可通过 API 人工重放 | "无限重试"会掩盖问题并浪费资源；死信让供应商长期不可用变成显式、可运维的事件。 |
| S5 | **幂等提交**：调用方可选传入 `idempotency_key`，对重复提交去重 | 业务系统对我们的调用自己也会重试（如网络超时后重发），没有这层我们会放大重复。 |
| S6 | **状态可见**：按 id 查询通知的状态与投递尝试信息 | 调用方和运维需要能回答"到底送到了没有"，而不是去翻日志。 |
| S7 | **崩溃恢复**：被 worker 认领后进程挂掉的通知，超过可见性超时后重新入队 | 重启不能丢任务、不能卡任务 —— 这就是题目里"可靠"二字。 |

### 2.2 明确不解决的问题（以及为什么）

| # | 排除项 | 理由 |
|---|-------|------|
| N1 | **供应商格式适配 / 模板化** | 调用方提交最终的 URL、Header、Body。按供应商适配格式是业务逻辑，应归属调用方（或未来的模板层）。保持本服务对 payload 无感知，边界才稳定：供应商格式常变，本服务永远不用跟着改。 |
| N2 | **恰好一次（exactly-once）** | 纯 HTTP 上不可实现：请求成功但响应丢失时，不借助接收方去重我们无法判定。我们透传 `X-Notification-Id` 头，让接收方*可以*去重，但不假装能保证。 |
| N3 | **顺序投递** | 跨通知的顺序需要按 key 串行化，与并发投递、重试调度天然冲突。题目给出的场景（广告转化、CRM 状态、库存）都不要求由*这条通道*保证严格顺序。列入演进项（§8）。 |
| N4 | **调用方鉴权 / 多租户** | v1 是可信内网上的内部服务。加鉴权后续很直接，但会消耗 MVP 时间且对核心问题没有展示价值。 |
| N5 | **SSRF 防护 / URL 白名单** | v1 的调用方是可信内部系统。作为安全事项记录在 §9；一旦出现半可信调用方则为必做项。 |
| N6 | **投递结果回调业务系统** | 调用方明确不关心结果。拉取式状态查询（S6）覆盖偶发的"送到了没有"需求。 |
| N7 | **按供应商限流 & 熔断** | 规模上去后是真实需求，但在 MVP 流量下为时过早。死信机制（S4）已经兜住了供应商长期故障的影响面。列入演进项（§8）。 |
| N8 | **管理后台 / 指标看板** | 结构化日志 + 状态 API 足以运维 v1。 |

## 3. API 契约

内部 HTTP API，JSON 格式。

### 3.1 `POST /api/notifications` — 提交通知

```json
{
  "target_url": "https://vendor.example.com/hooks/registration",
  "method": "POST",                        // 可选，默认 POST；限 POST|PUT|PATCH
  "headers": {"Authorization": "Bearer x", "Content-Type": "application/json"},
  "body": "{\"user_id\": 42}",             // 原样透传的 UTF-8 字符串
  "idempotency_key": "reg-42-2026-07-16"   // 可选，每个逻辑事件唯一
}
```

`body` 为 UTF-8 字符串，对内容格式无感知（JSON / XML / 表单均可）。
v1 不支持二进制 body；如需支持，base64 编码是演进方向。

响应：

- `202 Accepted` + `{"id": "...", "status": "pending"}` — 已持久化，投递责任移交本服务。
- `200 OK` + 已有记录 — `idempotency_key` 重复且 payload 一致（幂等重放，不算错误）。
- `409 Conflict` — `idempotency_key` 重复但 payload（target_url / method / headers / body
  任一）不一致。同一 key 复用在不同请求上是调用方 bug，报错暴露比静默返回旧记录更诚实。
- `400 Bad Request` — URL / method 非法，或 body 超限（上限 256 KiB）。

**202 就是契约**：一旦返回，调用方即可遗忘这条通知。

### 3.2 `GET /api/notifications/{id}` — 查询状态

返回完整记录：状态（`pending | delivering | succeeded | dead`）、尝试次数、
最近一次错误、下次重试时间、各时间戳。

### 3.3 `POST /api/notifications/{id}/redeliver` — 重放死信

将 `dead` 状态的通知重置为 `pending` 并给予全新的重试预算；非 dead 状态返回 `409`。
这是运维的抓手："供应商挂了两天，恢复后把死信重放一遍"。

### 3.4 投递请求（供应商实际收到什么）

与调用方提交的 method / headers / body 完全一致，另加：

- `X-Notification-Id: <id>` — 供接收方去重（见 N2）。

单次尝试超时：**10 秒**。**不跟随重定向**（会重定向的 webhook 属于配置错误；
跟随重定向等于悄悄改变投递目标）。

## 4. 数据模型

单表 `notifications`（SQLite）：

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | TEXT PK | UUIDv4 |
| `idempotency_key` | TEXT UNIQUE 可空 | 提交去重 |
| `target_url`, `method`, `headers`, `body` | TEXT | headers 为 JSON 对象 |
| `status` | TEXT | `pending` / `delivering` / `succeeded` / `dead` |
| `attempts` | INTEGER | 已完成的投递尝试次数 |
| `next_attempt_at` | TIMESTAMP | 调度键；与 `status` 建联合索引 |
| `claimed_at` | TIMESTAMP 可空 | worker 认领时间；驱动崩溃恢复 |
| `last_error` | TEXT 可空 | 最近一次失败描述（截断存储） |
| `created_at`, `updated_at` | TIMESTAMP | |

状态机：

```
             认领                  2xx
  pending ──────────► delivering ──────► succeeded（终态）
     ▲                    │
     │  可重试失败         │  不可重试失败（4xx）
     │  且预算未耗尽       │  或预算耗尽
     └────────────────────┼──────► dead ──(POST /redeliver)──► pending
       (next_attempt_at = 退避时间)
```

## 5. 投递语义与失败策略

### 5.1 语义：至少一次（at-least-once）

对比另外两种选择：

- *至多一次（at-most-once）* — 会静默丢通知，与题目唯一的硬需求直接矛盾；
- *恰好一次（exactly-once）* — HTTP 上不可实现（N2）。

重复可能出现在两处：调用方自身重试（由 S5 缓解）；以及**结果不明确**的场景 ——
例如供应商实际处理了请求，但我们等响应时超时了，随后重试。这是语义固有的，
`X-Notification-Id` 给了接收方去重的抓手。

### 5.2 单次尝试结果分类

| 结果 | 分类 | 动作 |
|------|------|------|
| 2xx | 成功 | → `succeeded` |
| 408、425、429、5xx | 可重试 | 退避后重试 |
| 网络错误 / 超时 | 可重试 | 退避后重试 |
| 其余 4xx | **永久失败** | 立即 → `dead` |
| 3xx | 永久失败（不跟随重定向） | 立即 → `dead` |

4xx 快速失败的理由：400/401/404 不会随时间自愈 —— 对着一个 bug 消耗重试预算，
只会推迟"有东西配错了"这个人工信号（死信）的出现。

### 5.3 重试计划

`delay(n) = min(base · 2^(n-1), cap) ± 20% 抖动`，默认值：`base = 5s`、`cap = 1h`、
`max_attempts = 12` → 大致为 5s、10s、20s……封顶 1h，总跨度约 **7 小时**。
三个参数均可配置。

判断依据：约 7 小时足以覆盖现实中的瞬时故障（发版、短事故），又不假装能覆盖
数天级的长期故障 —— 那是死信 + `/redeliver` 的职责。

### 5.4 供应商长期不可用

1. 封顶退避的重试自动吸收 7 小时以内的故障，无需任何人工介入。
2. 超出预算后通知进入 `dead` —— 通过状态 API 与日志可见。
3. 供应商恢复后，运维通过 `POST /redeliver` 重放（MVP 按 id 单条重放；
   批量重放是显而易见的演进项）。

这样，长期故障从"看不见的、不断膨胀的重试队列"变成**显式、可操作的运维事件**。

### 5.5 崩溃恢复

`delivering` 状态且 `claimed_at` 早于可见性超时（60 秒，> 单次尝试超时 10 秒）的行，
会被重新收回为 `pending`。后果：worker 在尝试中途崩溃可能造成一次重复投递 ——
与 at-least-once 语义一致，如实写入文档。

## 6. 架构

```
 业务系统 ──HTTP──► ┌────────────────────────────────────┐
                    │  单个 Go 二进制                     │
                    │  ┌──────────┐      ┌────────────┐  │      ┌────────────┐
                    │  │ HTTP API │─────►│  SQLite    │  │      │  供应商 A   │
                    │  └──────────┘ 事务 │ (WAL 模式) │  │ ┌───►│  供应商 B   │
                    │                    └─────┬──────┘  │ │    │  供应商 C   │
                    │                          │ 轮询    │ │    └────────────┘
                    │                    ┌─────▼──────┐  │ │
                    │                    │ dispatcher │──┼─┘  HTTP、超时、
                    │                    │ + workers  │  │     重试、退避
                    │                    └────────────┘  │
                    └────────────────────────────────────┘
```

- **单进程**：HTTP API + 轮询 dispatcher + N 个投递 worker（goroutine）。
- **SQLite 即持久化队列**（WAL 模式）。dispatcher 轮询到期任务
  （`status='pending' AND next_attempt_at <= now`），认领后
  （`pending → delivering`，写 `claimed_at`）交给 worker 池（默认 8 个）。
- **认领的原子性**：认领由单个 dispatcher goroutine 串行执行，用一条原子
  `UPDATE ... SET status='delivering' ... WHERE id IN (SELECT ... LIMIT k) RETURNING *`
  完成"选中即认领"，不存在双认领窗口。多实例部署时此模式失效 ——
  那正是演进第 1 步换 Postgres `SKIP LOCKED` 的触发点（§8）。
- **优雅停机**：停止认领，等在途尝试结束（受单次 10 秒超时约束）后退出。
  未完成的由 §5.5 兜底恢复。进程被 `kill -9`（无优雅停机机会）时，
  **仅**依赖 §5.5 的可见性超时回收 —— 实现不需要为此做任何额外处理。

### 6.1 关键决策：用数据库当队列，而不是消息中间件

MQ（Kafka / RabbitMQ / Redis Streams）是这道题的教科书答案 —— 但对 v1 是错的：

- 队列必须与 ack **同一事务**持久化（S1）。SQLite 在进程内同时给到这两点，
  运维面为零。
- "任意延迟的重试调度"在多数 broker 里很别扭（延迟队列、死信交换机的编排），
  在 SQL 里只是一列 `next_attempt_at`。
- 题目明确流量不大。引入 broker 等于多部署、多监控、多备份一套有状态系统 ——
  纯粹的运维成本，v1 没有任何收益。

**不用 SQLite 的替代方案**：Postgres + `SELECT ... FOR UPDATE SKIP LOCKED`
（同一套设计，可多节点）—— 这正是既定的演进第一步（§8）。存储层用小接口隔离，
让这次替换足够便宜。

## 7. 配置

环境变量，均有合理默认值：监听地址、DB 路径、worker 数、轮询间隔、
单次尝试超时、重试 base / cap / 最大次数、可见性超时。

## 8. 演进路径（流量 / 复杂度增长时）

按触发条件排序，而不是按技术时髦程度：

1. **吞吐超出单节点** → SQLite 换 Postgres（`FOR UPDATE SKIP LOCKED`）；
   只有认领查询这一处代码要改。之后跑 N 个无状态副本。
2. **慢供应商拖垮其他投递** → 按目标的并发上限与熔断器；在那之前，
   死信已经兜住影响面。
3. **写入量极高** → 在 DB *前面*加真正的 broker（Kafka）做摄入削峰；
   DB 仍是重试 / 状态存储。
4. **出现半可信调用方** → API 鉴权、URL 白名单、SSRF 防护（N4 / N5）。
5. **运维成熟度** → Prometheus 指标、批量重放、`succeeded` 行的保留 / 归档策略。
6. **接收方侧完整性** → HMAC 请求签名（webhook 标准实践）。

## 9. 安全考量（v1 姿态）

可信内网；无鉴权、无 URL 限制（N4 / N5）。Body 上限 256 KiB。
提交的 Header 中的密钥以明文存于 SQLite —— 对内网主机上的 v1 可接受，
已标记为演进第 4 步。

## 10. 测试策略

- **单元测试**：退避计算（增长、封顶、抖动范围）、结果分类（§5.2）、请求校验。
- **集成测试**（`httptest` 模拟供应商）：失败 N 次后成功 → 送达且尝试次数正确；
  永久性 4xx → 立即死信；预算耗尽 → 死信；redeliver → pending → succeeded；
  幂等键重放返回同一 id；同 key 不同 payload → 409；崩溃恢复回收（可见性超时到期）。
- 不做：压测（题目明确流量不大）。
